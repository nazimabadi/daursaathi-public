A personal running companion, built on top of Garmin

Daur Saathi

دور ساتھی  ·  daur (a lap, a round — also an era) + saathi (the one who is with you)

A tool that reads a runner's own Garmin data — pace, heart rate, sleep, splits, how a body's been holding up — and talks about it in plain language, through Claude. It reports, reflects, and asks. It does not command.

The name
Daur is a lap or a round, and — through the same root — an era: a lap of a run and a chapter of a life read the same way. Saathi is companion, specifically the one who runs alongside, not ahead.
Versus Garmin Connect
Garmin Connect describes a run. It doesn't know an injury history, doesn't hold more than one limiter at a time, and never asks how a session actually felt. Daur Saathi does, because it's been told, and it remembers.

Why it exists

Every design call here traces back to one rule, held on purpose against the pull of building something that just hands out verdicts.

Mirror, not driver
Reports what the data shows, offers options, asks questions — never prescribes. The decision always stays with the runner.
No sycophancy
No praise by default, no "great job." A good day and a bad day get the same plain treatment.
Observed vs. inferred
A measured fact and an educated guess are never allowed to look the same on the page.
Several limiters at once
Fatigue, an old niggle, a packed week — held together, never collapsed down to whichever one came up most recently.
Rolling over single
The trailing weeks matter more than any one run, on purpose — it's the fix for reading too much into a single bad day.

What it can actually do

Twelve tools Claude can call once it's connected. Eight only look things up. Four change something — three write down what the runner says, one pulls anything new in from Garmin.

12 tools  ·  8 read-only  ·  4 write
get_recent_runsreads

Lists the last several runs — date, duration, distance, pace, heart rate — and calls each one's actual character: easy, hard, steady, intervals, with the confidence behind the call. Garmin mislabels sessions often enough that this makes its own read rather than trusting the watch's tag.

get_training_loadreads

How much running has actually happened lately, and how this week sits against the last four — the difference between a normal week and a real spike or a real lull.

analyze_runreads

Pulls apart one run second by second: whether a hill genuinely cost extra effort, whether form drifted as fatigue set in, how much of it was actually run at a given pace. Shows the prior night's sleep and heart-rate context alongside it — the run itself is graded the same regardless, but the context changes how the result reads.

get_race_readinessreads

For a race with a goal time on record: how much of each week's training has genuinely been run at the pace that goal needs. Not a predicted finish time — just what's actually been proven in training so far, and whether it's trending up.

get_injury_historyreads

Turns scattered aches into episodes — when one started, how it's progressed, whether it's shown up during ordinary walking, which is the line between a niggle and something worth real attention.

get_flagsreads

Ten fixed rules checked against the data — the same body part sore three days running, severity climbing inside one episode. Rules, not opinions, so the answer doesn't shift with how the question was phrased.

adjust_sessionreads

"I've got 40 minutes and my calf feels off — what now?" Weighs the time available, the last few days' load, what's next on the plan, and last night's sleep, then lays out real options with honest trade-offs. Never picks one.

get_training_planreads

Reads back a plan written by hand — a statement of intent to check against, never a target being graded.

sync_latestwrites

Pulls anything new in from Garmin and analyzes it right away. Runs on its own every night, alongside a second pass that keeps sleep, heart-rate and stress data equally current.

log_symptomwrites

A new ache logged in the moment — body part, side, severity, what was happening — visible to the injury picture immediately.

log_subjectivewrites

How a run actually felt, in the runner's own words, kept verbatim rather than tidied — the phrasing itself is treated as real evidence, weighted above the heart-rate number for the same session.

log_quranwrites

Records a daily reading habit stacked alongside training — what was read, and what it was paired with (after fajr, before a run). Presence only: deliberately no streak, no score. A number would turn a quiet habit into a performance.

How it stays private

The interesting part isn't that an AI can read running data — it's what it's specifically never allowed to touch.

01

No password, ever

The Garmin login lives on its own server, never in a conversation. Claude only ever gets back the results of tool calls it's allowed to make — never the credential itself.

02

No GPS, anywhere

Location data is stripped before anything else touches a record. Not filtered out later — never stored to begin with.

03

One place only

No third-party analytics, no separate tracing service. The data goes exactly one place: into the conversation that's actually using it.

A personal project — built one runner's own tool, for their own training, on their own data.
